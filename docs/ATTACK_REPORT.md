# Attack report (internal round)

One round of attacks against BackedBy's own code, run after the offline suite passed and before anything was
deployed for real, plus a second round (H1 revised, H4, M5) after review of the first seeds. Every finding is written
as an attack in `test/test_attacks.py` or `test/test_vaults.py` that now fails, and every High and Medium is fixed in
commit **`91526ea`** (first round) or **`bf24598`** (second round) as the table says.

Scope of the round: unauthenticated pair tricks, block and timestamp games, decimals, proxy tokens, rebasing tokens,
re-entrancy of payouts, contest abuse, griefing, and whether the docs say what the code does.

| # | Severity | Attack | What happened before | Fix | Fix commit | Test |
|---|---|---|---|---|---|---|
| H1 | High | **Lookalike OP Stack token.** Deploy a contract on Optimism or Base that answers `remoteToken() = USDC` and `bridge() = L2StandardBridge`, mint 10^30 of it outside the bridge, and add it as a destination. | First fix (`0f4bf9b`): count `min(totalSupply, deposits)`. Second round found that this **hid** under-backing: a withdrawal burned on L2 leaves `totalSupply` at once but stays owed in `deposits` until paid, so a vault short of its own ledger could read BACKED. | Revised: count **`max(totalSupply, deposits)`**, which is at least the bridge's own ledger and at least every unit in circulation, so it can only err towards UNDER_BACKED (proof in RULES.md). | M1 | Medium | **Polygon mintable tokens.** Register a token whose RootChainManager type is `MintableERC20`: its L1 side is minted on exit, not released from escrow, so the predicate holds almost nothing and the pair reads UNDER_BACKED when it is not. | Any predicate type was accepted. | Only `tokenToType(l1) = keccak256("ERC20")` (the escrow predicate) authenticates. | `91526ea` | `M1PolygonMintable` |
| M2 | Medium | **Arbitrum non-escrow gateways.** Same idea on Arbitrum: a custom gateway that mints on L1 (or holds nothing) would read as under-backed. | Any gateway the router returned was taken as the vault. | Only the four gateways measured to escrow the L1 token are accepted (standard L1ERC20Gateway, L1DaiGateway via `l1Escrow`, L1USDCGateway, Lido's wstETH gateway); any other is refused at authentication and, through the anchors, at every check. | `91526ea` | `M2ArbitrumNonEscrowGateway` |
| M3 | Medium | **In-flight deposit flash.** Tokens locked on Ethereum but not yet minted on the destination count as locked and not as supply (that is the rule that keeps in-flight transfers from ever looking under-backed). A depositor can bridge a large amount and file a monitoring check at that instant to get one BACKED ruling for a pair the patrol has just found UNDER_BACKED, and the gate would have said yes for its whole max age. | The gate looked only at the latest ruling. | The registry keeps `last_bad_time`, the newest pinned time of any ruling that was not BACKED (UNDER_BACKED, or an INCONCLUSIVE about the pair's data). CollateralGate refuses while any such ruling is inside its max age. A flash cannot save a bond: the challenger picks the blocks, and in-flight deposits only add to locked. | `91526ea` | `M3InFlightDepositFlash` |
| M4 | Medium | **Junk-pin monitoring griefing.** File a monitoring check with pins that break the rules (gap over 10 minutes) once per monitoring interval. It closes INCONCLUSIVE, but it used up the pair's rate limit, so the patrol could never get a fresh ruling and the gate went stale. | The rate limit counted filings. | The interval counts only monitoring checks that were **ruled** on the pair's data (a verdict, or a data INCONCLUSIVE). A junk filing still occupies the pair until someone reads and rules it, which anyone may do; the patrol does it for every open check it finds. | `91526ea` | `Monitor.test_junk_pins_do_not_use_up_the_rate_limit` |
| L1 | Low | **Contest as a free delay.** The losing side contests and nobody re-reads; at the contest timeout the first ruling stands and the contest stake is refunded. | Bounded delay (2 h canonical) with nothing to gain: the bond cannot be withdrawn while the check is open. | Accepted. ## Milestone round (v2): coverage, new bridges, recovery, keeper, gate meaning

Run against the v2 code (Wormhole and CCIP templates, coverage scans, ledgers, PoR, history, PENDING reads, the
pair-bound gate and the keeper) before any v2 contract was deployed. Every High and Medium is fixed and has a test;
nothing of either severity is left open. H6 was found by the v2 demo on chain, after the first v2 deployment, and fixed before the deployment the seeds and demo below run on.

| # | Severity | Attack | What happened before | Fix | Test |
|---|---|---|---|---|---|
| H6 | High | **A large pair could never be ruled.** Found on chain in the v2 demo (registry `0xACf1d85b`, check 4: USDT on Polygon with two vaults and 13 destinations, a 19.5 KB request): `rule` crashed with `JSONDecodeError: Invalid control character at char 15648`, every time. Reproduced on Studio with a probe (test/probe/RuleProbe.py): Studio's runner returns a long string field (about 10 KB and up) corrupted when it is read through a struct reference **after another struct was looked up in the same call**; small fields, writes and fresh lookups are fine. `rule` read the check's request, looked up the pair, then read the request again. A check with a reading cannot be expired, so the pair, its bonds and its monitoring stayed blocked. | Two reads of the same field were assumed equal. | First fix (`61a08f8`, fresh lookups) was not enough: the demo on its deployment failed the same way (check 4 at char 15648, check 16 at char 4352), because a second read of the same field is corrupted even through a fresh lookup. Final fix: every write reads each long field (requests, rulings, payouts, a pair's destinations, vaults, anchors and lists) **once**, right after looking the record up, and passes the parsed value on (`rule`, `finalize`, `expire`, `challenge`, `monitor`, `_settle`, `_history`); a static test forbids any other read; the offline stub models the runner exactly (a second read of the same long field after any lookup comes back corrupted) and fails the `61a08f8` code; full flows run with every field counted as long. Proved on Studio on the 13-destination USDT pair before the deployment the seeds and demo run on. | `test_v2.LongStringFields` (5), all suites under the new stub | | H5 | High | **Unlisted destination.** A vault backs a token on a chain its pair does not list (USDT0's adapter had peers on six chains BackedBy did not read; a CCIP pool can add a chain at any time). The unlisted supply is owed from the same vault, so the pair reads better backed than it is, and the gate said yes. | Accepted in v1's Scope ("their supply is not counted"). | Every check now records each vault's **coverage** at the pinned Ethereum block from the bridge's own config: LayerZero adapters are scanned for a peer on every eid in 30101-31100 in one Multicall3 call; CCIP pools list `getSupportedChains()`; Wormhole's ledger `outstandingBridged` (what it owes on every chain) is counted as supply when larger than the listed tokens; single-mapping bridges are complete by construction; OP/Base escrows and Nomad cannot be enumerated and are OPEN. The gate is favorable only for COMPLETE. The keeper adds every unlisted destination it can prove and records the rest as unmatched; the site shows both. | `test_v2.Ccip`, `LayerZeroScan`, `Wormhole.test_ledger_*`, `test_meaning`, `keeper.test.mjs` discovery |
| M6 | Medium | **One lying RPC parks the gate.** A single RPC operator answers one call differently; v1 recorded `INCONCLUSIVE · RPC_DISAGREE` as the pair's latest ruling and moved `last_bad_time`, so CollateralGate refused the pair for its whole max age. | A transport fault became a ruling about the pair. | Transport faults (an RPC down, throttling, or a chain's two RPCs differing) are **PENDING**: nothing is stored, the check stays OPEN, anyone retries until the read window fixed at filing closes, then it expires and refunds. A validator accepts a leader's PENDING only if its own read fails too. | `test_v2.BoundedRecovery`, `test_reader`, `test_attacks.Decimals` |

| M8 | Medium | **Hiding a peer behind a revert.** An adapter whose `peers(eid)` reverts for one eid looked like "no peer". | `allowFailure` entries read as empty. | A reverting entry makes the scan UNREAD. | `LayerZeroScan.test_a_reverting_peer_entry_is_unread` |
| M9 | Medium | **Scan flakiness stalls every read; a leader invents coverage.** Validators compared the whole reading; one flaky scan RPC made reads UNDETERMINED, and loosening that naively would let a leader claim COMPLETE. | Liveness depended on the least reliable endpoint. | Verdict fields must be identical; a leader's scan or PoR entry that is an error is accepted (it can only make the answer less favorable); a leader's entry with data must equal the validator's own read. | `test_v2.ValidatorTolerance` (6 tests) |
| M10 | Medium | **Copycat answers.** `is_backed(pair, now)` answered for whatever pair id it was given, so a market that looked up a pair id from an untrusted list read a copycat (the same tokens under a lax tolerance) or another token's pair. | Pair-only binding. | Every gate question names the pair **and** its source token and destination (chain, token); anything else is `NOT_THIS_PAIR`. | L9 | Low | **Pool labels.** A CCIP pool's `typeAndVersion` is set by the token's admin; a pool that calls itself lock-release but holds nothing reads UNDER_BACKED. | Accepted: it can only err towards UNDER_BACKED, and only an operator who chose to bond that pair is exposed. | - | `Ccip.test_*_refused` |

## Also checked, nothing found

- **Fake vaults.** An attacker's adapter whose `token()` is USDT and whose OFT, peers and Polygon token are the
  attacker's own authenticates (it is a real OFT setup), but only against the attacker's token, so `add_vault` and
  `add_destination` refuse it for the USDT pair; pointing a fake adapter's peer at the real Polygon OFT does not help,
  because the adapter is derived from the real OFT's `peers(Ethereum)`.

- **Fake pairs.** A plain ERC-20, an EOA, Circle's native USDC on OP passed off as bridged USDC, a token on the wrong
  chain for its bridge kind, a Nomad representation from another domain, a source token Nomad does not hold as local:
  all refused at authentication (`test_reader.py`), and on Studio Dev with real chain data (native USDC on OP,
  `REMOTE_TOKEN_IS_NOT_THE_SOURCE_TOKEN`).
- **Omitted destinations.** An operator registers only one of two Standard Bridge representations; anyone adds the
  other with the same proof and the next check counts it (`Destinations.test_omitted_destination_cannot_hide_supply`).
- **Timestamp games.** Destination newer than source by one second, gap of exactly 600 s (rules) and 601 s
  (INCONCLUSIVE), Polygon 300/301 s, swapped block numbers, blocks above either RPC's finalized block: all decided by
  code, with the stake refunded where the filing was at fault.
- **In-flight transfers inside the gap** only ever over-back (`BlockGames`), as RULES.md argues.
- **Forged leaders.** A leader that alters a vault, a decimals value, a balance or claims an INCONCLUSIVE it did not
  observe is outvoted (`test_reader.py`, `FORGE`).
- **Payables.** None of the four payable methods contains a `raise` (AST test); garbage arguments refund.
- **Stuck states.** Every non-terminal state reaches FINAL or INCONCLUSIVE through a permissionless call after its
  deadline, including with every RPC down forever (`StuckStates`).
- **Conservation.** A 160-step random sequence of every operation keeps `received = bonds + open + claimable +
  claimed` after every step and drains to zero (`Conservation`).
